E-DX — Documentação Técnica Interna

Referência oficial de engenharia para manutenção e evolução do E-DX: o middleware .NET que conecta o SAP ao mundo fiscal (SEFAZ, prefeituras, Siscomex) por RFC, SOAP, e-mail e HTTP.

Este documento cobre a arquitetura completa do sistema, a estrutura da solução, a ponte de comunicação SAP⇄.NET (com o catálogo completo de RFC Server Functions e o cruzamento com os métodos ABAP de /XEGR/CLEGR_EDX) e o funcionamento de cada módulo de domínio fiscal: NFe, NFSe, DUE/DUIMP, E-mail, Certificados/segurança, CTe, MDFe, GNRE, FCI, EGRF e EGTS.

Fora do escopo desta versão: as camadas E-DX-API/E-DX-WEB (rotas HTTP) e o aplicativo desktop E-DX (WinForms) ainda não foram documentados em profundidade — ver Escopo e itens pendentes.

Convenções deste documento

Toda afirmação técnica é rastreável ao código-fonte (.NET) ou aos métodos ABAP exportados que a sustentam. Onde uma relação entre SAP e .NET não pôde ser confirmada por chamada direta (por exemplo, Function Modules referenciados pelo ABAP que não têm implementação no pacote .NET analisado — provavelmente residentes apenas do lado SAP), isso é indicado como Presumido; o restante do conteúdo é tratado como confirmado. Ver Cruzamento ABAP⇄.NET.

O menu lateral segue a estrutura de camadas do sistema: fundação (arquitetura, estrutura, ponte SAP⇄.NET), módulos de domínio fiscal e referência. Use a busca no topo do menu para pular direto a uma classe, RFC ou palavra-chave.

Arquitetura geral

O E-DX é um middleware fiscal: ele fica entre o SAP (ECC/S4) e o mundo externo (governo, prefeituras, e-mail), fazendo o SAP falar XML/SOAP/RFC com sistemas que ele não fala nativamente.

A direção SAP→.NET é confirmada no código: E-DX-SRV registra um RfcServer via SAP NCo (SAP.Middleware.Connector) usando clsSAPServerFun como handler. O SAP chama o .NET (RFC Server Program registrado), não o contrário — ver Ponte SAP⇄.NET.

Componentes da arquitetura

SAP ECC/S4 + classe /XEGR/CLEGR_EDX

Camada ABAP que decide quando chamar o E-DX (ex: baixar XML de NFe, enviar e-mail de manifestação, verificar assinatura) e resolve qual destino RFC usar por empresa/filial/função.

RFC / SAP NCo

SAP.Middleware.Connector é a biblioteca .NET oficial da SAP (NCo) usada nos dois sentidos: como servidor RFC (SAP chama o .NET) e como cliente RFC (o .NET pode chamar de volta o SAP, via clsSAPClientCon/clsSAPClientFun).

E-DX-SRV (Windows Service)

Processo de fundo que hospeda o RFC Server. É o coração operacional do sistema — fica sempre rodando, ouvindo chamadas do SAP.

E-DX-LIB

Biblioteca de classes compartilhada por todos os front-ends (serviço, API, WinForms) — contém toda a lógica de negócio por domínio fiscal.

E-DX-API / E-DX-WEB (IIS)

Expõe parte da funcionalidade via HTTP: WebEdxController, SIAController, FLOWLSController (API REST) e wbsedx.asmx (web service SOAP legado).

E-DX (WinForms)

Aplicação de desktop para configurar empresas/certificados, testar conexões (SAP, e-mail, internet) e operar o serviço manualmente.

Governo (SEFAZ / Prefeituras / Siscomex)

Web services SOAP (NFe/CTe/MDFe via SEFAZ), SOAP/REST heterogêneos por prefeitura (NFSe) e REST com OAuth2 (Siscomex DUE/DUIMP).

SMTP / IMAP / POP3

Módulo MAIL usa bibliotecas de terceiros embarcadas (OpenPop, OpenImap) mais OAuth2/Graph para ler e-mails de manifestação e anexos XML de fornecedores.

Nota de escopo: os detalhes internos de E-DX-API/E-DX-WEB (rotas, contratos DTO) ainda não foram documentados a fundo — os controllers foram apenas indexados (WebEdxController, SIAController, FLOWLSController). Ver Escopo e itens pendentes.

Fluxo geral (ida e volta)

Existem, na prática, dois fluxos distintos confirmados no código — é importante não confundi-los:

1. SAP → Governo (o caminho mais comum: SAP inicia)

sequenceDiagram participant ABAP as SAP/ABAP participant GW as Gateway RFC participant SRV as E-DX-SRV participant FUN as clsSAPServerFun participant BIZ as E-DX-LIB participant GOV as Governo ABAP->>ABAP: get_rfc_destination(bukrs, branch, function) ABAP->>GW: CALL FUNCTION '/XEGR/FGR_xxx' DESTINATION rfcdest GW->>SRV: invoca Function Module registrado SRV->>FUN: dispara método [RfcServerFunction] FUN->>BIZ: delega para classe de domínio BIZ->>BIZ: monta/valida XML BIZ->>GOV: SOAP/REST (assinado quando aplicável) GOV-->>BIZ: resposta XML BIZ-->>FUN: retorno + tabela de saída FUN-->>GW: parâmetros de saída RFC (pstaret, pmotret...) GW-->>ABAP: resposta síncrona

2. .NET → SAP (caminho inverso — confirmado como capacidade, uso pontual)

A classe clsSAPClientFun (1125 linhas) e clsSAPClientCon (implementa IDestinationConfiguration) dão ao .NET a capacidade de chamar function modules do SAP como cliente RFC — por exemplo, para gravar retorno de processamento de volta na base SAP. Presumido: não está determinado quais métodos de clsSAPClientFun são chamados por qual fluxo de negócio — fica para a fase de aprofundamento por módulo.

Consequência prática para manutenção: se uma chamada do SAP "não retorna nada", o primeiro lugar a olhar não é a rede — é clsSAPServerFun (o método RFC específico) e depois a classe de domínio que ele delega. Se o SAP "não recebe atualização de status", o suspeito é clsSAPClientFun/clsSAPClientCon.

Comunicação SAP ⇄ .NET

Fontes: E-DX-SRV/EDX_SRV.cs, E-DX-LIB/SAP/*.cs

A ponte usa o SAP Connector for Microsoft .NET (NCo), pacote SAP.Middleware.Connector. Cinco classes formam a ponte:

ClasseInterface SAP NCoPapel
clsSAPServerConIServerConfigurationFornece os parâmetros de registro do .NET como servidor RFC (Program ID, Gateway) — usado para o SAP chamar o .NET.
clsSAPServerFunhandler com métodos [RfcServerFunction]Onde cada Function Module RFC é implementado em C#. 1973 linhas, 78 funções registradas (ver catálogo).
clsSAPServerHandlerITransactionIDHandlerControle de tRFC (commit/rollback/confirm por Transaction ID). implementado mas não registrado — a linha que o ativaria em EDX_SRV.cs está comentada.
clsSAPClientConIDestinationConfigurationFornece parâmetros de conexão de saída (.NET → SAP), incluindo suporte a Load Balancing (Message Server) ou conexão direta.
clsSAPClientFun—Métodos que o .NET usa para chamar function modules do SAP como cliente. 1125 linhas.
Segurança: ambas as classes de conexão suportam SNC (Secure Network Communications) — UseSNC ativa SncMode=1, SncQOP=9 e aponta para C:\SAPCrypto\sapcrypto.dll. É condicional por configuração de empresa (clsConfigItem.UseSNC), não obrigatório.

RFC Server Functions — detalhamento completo

clsSAPServerFun.cs (1973 linhas) registra 78 funções via [RfcServerFunction(Name="...")], organizadas em 7 blocos (#region no código-fonte): E-GR (NFe/NFSe/E-mail/status), E-GTS (Siscoserv), E-GTE (DUE), E-GTI (DUIMP/IA), E-GRF (EGRF), E-GNRE (GNRE) e E-CI (FCI). Esta seção documenta, para cada função, o parâmetro de entrada, o processamento e o parâmetro de saída — a referência para diagnosticar qualquer chamada que "não funciona".

Padrão de execução comum (bloco E-GR)

Toda função do bloco E-GR — a grande maioria das 78 — segue exatamente o mesmo esqueleto:

log nivel E"] F --> I["mvarSTATUS = STOPPED"] G --> I H --> I
ElementoDetalhe
clsActualItemCampo estático da classe (public static clsConfigItem clsActualItem). É atribuído uma única vez em EDX_SRV.cs na inicialização do serviço (clsSAPServerFun.clsActualItem = varclsConfigList.clsActualItem) a partir da empresa resolvida por /EMP=, e reatribuído periodicamente pela rotina de verificação de conexão. Como é estático, todas as chamadas RFC atendidas por essa instância do serviço compartilham o mesmo objeto de configuração/certificado — coerente com a arquitetura de uma instância de serviço por empresa.
mvarSTATUSFlag de estado (RUNNING/STOPPED) da última função em execução — útil para saber, olhando o processo em memória, se o serviço está no meio de uma chamada.
Categoria de logString fixa por função (ex: "ENFE", "EGTS", "EGRF", "GNRE", "XBR") — é o campo usado para filtrar o log do dia (ver arquivo de log). A maioria das funções do bloco E-GR usa "ENFE" mesmo quando a operação não é NFe (ex: e-mail, conversão de PDF) — ao procurar um problema no log, filtrar só por categoria pode esconder o evento; é mais confiável filtrar pela tag "clsSAPServerFun:funcXXX" que acompanha cada linha.
Prefixo /XEIT/ vs /XEGR/Confirmado em código: a versão /XEIT/ contém a implementação real; a versão /XEGR/ é um método separado que só chama a /XEIT/ internamente (ex: funcEGR_MDDOWNNFE chama funcEIT_MDDOWNNFE). São dois nomes RFC distintos no SM59 apontando para o mesmo processamento.
Erro convertido em "E000 - " + MessageToda exceção não tratada dentro do método de negócio chega ao SAP como uma string começando com E000 — a stack trace original não é logada na maioria dos casos (só o .Message), o que limita o diagnóstico a partir do log do E-DX sozinho; muitas vezes é necessário reproduzir a chamada para ver a exceção completa.

Três convenções de retorno diferentes coexistem no mesmo arquivo

ConvençãoOnde é usadaComo interpretar
PSTARET / PMOTRETBloco E-GR (NFe, NFSe, e-mail, assinatura) — convenção legadaPSTARET é o código de status ("100"/"140" = sucesso variantes, "ERR"/"E000"/"999" = erro); PMOTRET é a mensagem/motivo em texto
ET_RETURN (tabela BAPIRET2)/XEGT/FEDX_DUIMP (envio de DUIMP)Convenção padrão SAP (BAPI Return Table): TYPE (E=erro, S=sucesso), NUMBER (código, ex: "404" para falha de autenticação), MESSAGE (texto) — só é populada explicitamente no caminho de erro de autenticação; nos demais caminhos a função retorna sem preencher nada

Implicação prática: não existe um único "código de erro" a procurar em todo o sistema — o significado de sucesso/erro muda conforme o bloco. Ao investigar uma função, primeiro identificar a qual dos três grupos ela pertence antes de interpretar o valor de retorno.

Todo método de comunicação com a SEFAZ segue o mesmo esqueleto: (1) checa conectividade (clsFunction.funcInternetIsOnline()) (2) resolve o certificado digital da empresa/CNPJ (pclsConfigItem.funcGetCertificate) (3) resolve a URL/versão do webservice por UF e ambiente via clsNFeWbsConfig.funcGetXMLParameters (4) monta o XML de envio como string concatenada (5) cria o cliente SOAP tipado (classes clsNFeConsDocs, clsNFeDownload etc., geradas a partir do WSDL da SEFAZ) com o certificado anexado (6) chama o webservice (7) lê cStat/xMotivo da resposta e decide sucesso/erro (8) grava os campos de saída na função RFC (PSTARET, PMOTRET) para o SAP ler de volta.

Achado de segurança (ver detalhe em Certificados & segurança): em funcDownloadDoc, a validação do certificado do servidor SEFAZ é explicitamente desabilitada: ServicePointManager.ServerCertificateValidationCallback = clsValidadeCertificatePolicy.NotValidServerCertficate, método que sempre retorna true. Isso significa que a comunicação HTTPS com a SEFAZ não valida se o certificado apresentado pelo servidor é confiável — está sujeita a MITM caso a rede não seja de confiança.

Nota de segurança — confirmado em 3 pontos independentes do código:

clsValidadeCertificatePolicy.NotValidServerCertficate(...) sempre retorna true, independente do resultado real da validação de cadeia/TLS: 
public static bool NotValidServerCertficate(object sender, X509Certificate certificate, X509Chain chain, SslPolicyErrors policyErrors) {
    return true;
}
Esse método é atribuído a ServicePointManager.ServerCertificateValidationCallback em pelo menos três fluxos confirmados: clsModuloNFe.funcDownloadDoc (comunicação com SEFAZ), DUEAuthentication.loginHandshake e DUEREST.dueRequest (comunicação com Siscomex). Na prática, isso desliga a checagem de que o servidor remoto (SEFAZ/Siscomex) é quem diz ser — o TLS ainda criptografa o canal, mas não impede um ataque man-in-the-middle com certificado forjado.

Existe também um método legado ValidateServerCertficate (marcado [Obsolete]) que respeita SslPolicyErrors.None a menos que a chave IgnoreSslErrors do app.config esteja ativa — ou seja, o sistema já teve uma validação correta e opcional, e o código atual usa a versão que sempre ignora.

Se isso for intencional (por exemplo, para lidar com certificados intermediários da SEFAZ mal configurados em produção — problema comum no ecossistema fiscal brasileiro), recomenda-se documentar a decisão explicitamente no código; caso contrário, trata-se de uma vulnerabilidade a corrigir.

Autenticação por certificado do cliente (mTLS) é usada de duas formas distintas: certificado e-CNPJ da empresa (pclsConfigItem.funcGetCertificate, usado em NFe/NFSe/EGRF) e certificado e-CPF do responsável (profile.funcGetCertificateECPF, usado em DUE/DUIMP) — o corpo desses dois métodos de resolução de certificado (prováveis em clsConfigItem.cs) não documentado em detalhe — não é possível confirmar de onde exatamente o certificado é carregado (Windows Certificate Store vs arquivo .pfx).

CTe · MDFe · GNRE · FCI · EGRF/EGTS

Cada um documentado a partir de sua classe orquestradora. por leitura de assinaturas.

CT-e (Conhecimento de Transporte)

CTE/Controller.cs: manifestoDocCTe e manifestoDocCTe2 (internal static — só acessíveis dentro do assembly, chamadas via clsModuloNFe.funcConsultaDocsCTe/funcConsultaProtCTe, que reusam a infraestrutura de NFe para o fluxo de CT-e). Confirma que CT-e não tem orquestrador RFC próprio — ele é tratado como uma variação do módulo NFe.

MDF-e (Manifesto de Documentos Fiscais)

MDFE/clsModuleMDFe.cs: funcConsultaDocs (mapeia GET_MDFE_58) e SaveMDFeDocument (grava o XML retornado). Módulo mais enxuto dos seis — só uma operação de consulta/download, sem manifestação/cancelamento próprios encontrados nesta classe.

GNRE (Guia Nacional de Recolhimento de Tributos Estaduais)

GNRE/clsModuleGNRE.cs: batchTransmitRequest e batchTransmitResponse — mapeiam exatamente FGNRE_BATCH_TRANSMIT e FGNRE_BATCH_TRANSMIT_RES do catálogo. Padrão request/response assíncrono em lote: o SAP dispara o lote (request) e depois consulta o resultado (response) numa segunda chamada — não é síncrono como a maioria dos outros fluxos.

FCI (Ficha de Conteúdo de Importação)

FCI/clsModuloFCI.cs — o módulo com fluxo de estágios mais explícito de toda a base, 5 métodos em sequência clara: funcSimularArquivo → funcValidarArquivo → funcGerarMidiaArquivo → funcRecuperarMidiaArquivo → funcTransmitirArquivo, com flags de estado correspondentes (ArquivoSimulado, ArquivoValidado, GeradoMidiaArquivo, ArquivoTransmitido). Usa a biblioteca oficial da Fazenda de SP embarcada: Br.Gov.Sp.Fazenda.CCI.ValidadorFCI — ou seja, a validação de FCI não é reimplementada, é delegada ao validador oficial do governo. Subpasta GOV/ tem ~15 classes de layout de arquivo (estrutura posicional do arquivo-mídia FCI).

graph LR A[funcSimularArquivo] --> B[funcValidarArquivo] B --> C[funcGerarMidiaArquivo] C --> D[funcRecuperarMidiaArquivo] D --> E[funcTransmitirArquivo]

EGRF (e-Gestão de Riscos Fiscais / Programação de Embarque)

EGRF/Controller.cs: sendEventNFe, docConsultSefaz (ambos internal static, retornam EGRFreturn) e um método privado assinar(xml, certificate) — ponto de assinatura digital próprio, dedicado a este módulo, separado da assinatura genérica de clsModuloNFe. Mapeia as funções FGRF_* do catálogo.

EGTS / Siscoserv

EGTS/clsModuloSiscoServ.cs: funcSendFile (mapeia FGTS_SENDFILE) e funcGetStatus (mapeia FGTS_GETSTATU), mais funcCheckSchema/ValidationEventHandler — validação de XSD explícita antes do envio, único módulo onde essa validação de schema aparece nomeada dessa forma no orquestrador (os outros módulos validam implicitamente via biblioteca de terceiros ou não validam localmente).

Padrão transversal observado nos 6 módulos: cada um tem exatamente uma classe orquestradora "fina" (Controller ou clsModulo*) que clsSAPServerFun chama diretamente, e a complexidade real (parsers de layout, clientes SOAP gerados, regras de schema) fica em classes auxiliares na mesma pasta — nenhuma delas foi detalhada corpo a corpo neste documento.

Fontes e rastreabilidade

O conteúdo deste documento é derivado diretamente de duas fontes: o código-fonte .NET do E-DX e os métodos exportados da classe ABAP /XEGR/CLEGR_EDX. O cruzamento entre os dois lados foi feito por correspondência exata de nome entre as chamadas CALL FUNCTION ... DESTINATION do lado ABAP e os 78 métodos [RfcServerFunction] registrados em clsSAPServerFun do lado .NET (ver Catálogo de RFC Server Functions e Cruzamento ABAP⇄.NET).

Cada módulo de domínio foi documentado a partir de sua classe orquestradora — a classe que clsSAPServerFun chama diretamente para executar a operação de negócio. As classes auxiliares por trás de cada orquestrador (clientes SOAP gerados, parsers de layout específicos, integrações individuais por prefeitura no caso de NFSe, entre outras) não estão detalhadas linha a linha — ver Escopo e itens pendentes.
